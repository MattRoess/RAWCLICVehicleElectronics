`PCBAreaMC` had its sampling in one vectorised function that could be wrapped.

(segments × motor types × materials), so chunking means restructuring the script
body. Runs take several minutes, so the verify cycle is slow. **Do it with room
to spare** — a half-restructured Monte Carlo loop produces plausible wrong
numbers, not an obvious failure.

**Not a blocker for M-c:** at 51 years the arrays reach ~82 MB per metric.
Uncomfortable, not the 12 GB that made it mandatory for PCB. **M-c can go first
if preferred.**

## 3. Open decisions — these need the user

1. **PDF export resolution.** M-b1 took motor histograms 140 → 50 bins for
   suite comparability, which **coarsens the PDF users receive**.
   `tools/accumulator.py` holds 1000 bins internally and `coarse(s, n_out=...)`
   emits any divisor of 1000. **Decide at M-b2:** export a finer PDF alongside
   the comparable 50-bin one, or accept 50.
2. **`12_Motor_Distribution.csv`** is generated by
   `BEVElectronicsClassification.py` and **read by nothing**. Rename it to say
   it is an ECU-attributed view, or stop generating it.
3. **`P-g`** — how far zonal consolidation collapses the other ~49
   controller-like components. **50.7% of EF board area, unsourced.** The
   largest open item in the whole PCB chain.
4. **Motor anchors** (`05_` sheet `Motor_Growth`): headroom AB 1.30/1.50/1.80,
   CD 1.20/1.35/1.60, EF 1.05/1.15/1.30; τ 20/30/50 y. **The only invented
   numbers in the motor design.** Change them there if they look wrong.

## 4. What the models now say — and how to quote it

**PCB area, 2025 → 2070:** AB +0.4%, CD −1.1%, EF −2.0%.
**Element mass:** AB −0.30%, CD −1.41%, EF −1.68%.

**These are NOT a forecast that BEV electronics material demand is flat.** They
are the measured reach of the architecture driver **as scoped** — 8.2% of board
area. A driver reaching 8.2% cannot move a total by more than a few percent.
**P-g's 50.7% pool is where a real trend would come from.** Quoting the numbers
without that sentence misrepresents them.

Same for motors when built: expect AB ≈ +39%, EF ≈ +12% by 2070, with **35 of
the 50 years being extrapolation** — every source stops at 2035.

## 6. Standing rules — these matter more than the backlog

- **Only the user says when work moves forward.** No modification without an
  explicit OK. Agreement with an idea is not permission to edit.
- **Investigate before correcting. Document before implementing. Keep reports in
  line with the code and the results.**
- **No dead parameters. No unsourced parameters.**
- Large uncertainties are the point; >10× is the threshold for calling something
  an error. **Predictions are scenarios with uncertainty, not science.**
- `ElectricMotorMC` is **auxiliary** motors, not traction.

### Three traps that have each bitten once

1. **Adding a sheet to a workbook can break readers** that apply fixed
   `usecols` to every sheet (`01_`, 2026-08-09, broke both sensor models).
   **Check the reader before writing.**
2. **Footnotes in a data column** silently change the row count
   (`Presence_per_Tier` read 13 rows for 12; `BASE_YEAR` did it again in
   `Motor_Growth`). **Park them in a far column.**
3. **Non-breaking spaces in `11_` component names** (`Body\xa0Control\xa0Module`).
   Exact-match lookup returns nothing **with no error**. Normalise whitespace.

### And one about method

Three times on 2026-08-11 I wrote a mechanism this project had **already
solved** — the V13 presence rule, `_shift_shares`, and the accumulator. Each was
sitting in `SensorNumbersMC` or `BevWiring`. **Ask "has this been solved here
already?" before designing.** The user caught the first two.
